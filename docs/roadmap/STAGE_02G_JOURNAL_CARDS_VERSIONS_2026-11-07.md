## Implementation

- Journal groups remain chronological/accessible by group label, but no longer repeat full visible date banners. Ordinary note cards have *only the user's main text* plus optional authored title. Legacy automatically generated Russian date headings remain in Firestore untouched but are hidden visually. New notes no longer receive a fabricated date title.
- One subdued footer timestamp, after deliberate whitespace; icon-only pencil, revision history and append existing note flow with accessible labels/tooltips. No duplicate date inside the note text body.
- Only newly server-confirmed note creation gets a gentle 430 ms fade+rise. On reload, filtering and restoring older notes do not trigger the new-item transition. Reduced-motion preference disables the transition.
- A note document already stores an ordered \`entries[]\` array; individual appended fragments are separate chronological timeline events. The timeline now carries \`entryIndex\` for precise edit scope.
- Editing an individual fragment uses Firestore \`runTransaction\` on the same **UID-owned diaryNotes document**. It reads the latest document, checks the expected version, saves the **previous text and title** in that fragment's \`versions[]\`, then writes updated text and optional per-fragment \`displayTitle\`. Existing \`createdAt\`, other entries and all previous versions remain unchanged. The current version is displayed alongside its full history. Concurrent stale versions fail with a visible error and keep the unsaved editor text; ambiguous retries are idempotent by \`lastEditId\`. No silent history truncation; editing fails safely near an 800 KB encoded document budget.
- The earlier create flow's Firestore-confirmed ID echo and the authoritative \`onSnapshot\` remain intact. A new transaction-confirmed edited record has a short-lived ID/version-based UI echo until the current server snapshot catches up; it must never resurrect a deleted note.
- The legacy "Дополнить заметку" action still appends via the existing application modal. This is not the edit operation.
- Existing client-only AI send remains disabled until a secure server backend exists. No AI-generated titles or fabricated history.

## Limits / future work

- Versions reside inside the same existing Firestore note document, not an append-only server audit log. The owner may inspect every in-document saved version; protection from malicious owner-controlled rewriting is **not** promised, and Firestore has a document size limit. Proper tamper-evident immutable audit history would require separate protected subcollections and a redesigned export/restore/rules workflow.
- No auto-migration or deletion of historical date titles; only UI projection changes.
