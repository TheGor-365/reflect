## Принципы теста

1. Один **реалистичный вымышленный персонаж от первого лица** (веб-разработчик с двумя предполагаемыми заказчиками), одна проблема и последующий результат. В саму реплику не вставлять команды «это тест», «создай JSON», «сгенерируй KPI» — проверяется натуральное поведение продукта. Снаружи заранее фиксируется: **всё вымышлено; к реальным фактам Eric не относится**.
2. Сохранять **одну последовательную историю**, проходить: первоначальное описание → уточнение/опровержение гипотез → выбор шага/цели → ретроспективный результат → отдельный сеанс для **проверки ограничения памяти**, а не невыполнимого автопереноса истории.
3. **Пока только один осознанный реальный платный запрос за раз.** Обычная кнопка отправки, не «Контекст и история». Каждый запрос сохраняется в staging Firestore, может потребить xAI квоту. При тайм-ауте или сомнительном ответе **не повторять** без проверки receipt/status; backend stage онлайн не гарантирует outbound.
4. Отдельно различать: **AI сгенерировал** / **интерфейс детерминированно спроецировал из сохранённых данных** / **владелец подтвердил действием** / **должно быть разработано** / **не проверено**. Не считать отсутствие выдуманной автоматически подтверждённой причинной связи дефектом защиты.
5. Приватность: все тестовые данные **фиктивны**, не предоставлять другие реальные сеансы, не публиковать user UID, токены, email, полные диалоги со сторонними данными в GitHub. Для evidence достаточно обезличенных наблюдений: скрин с новым synthetic session, поля, статусы, префикс версии/тайминги без секретов.
6. Режим provider cross-session history **BLOCKED**, Ledger R10 только в Emulator, клиентская запись в доверенные `memoryEvents`, `memoryProjections`, `memoryControl/erasure` не защищена на живом staging (обнаружено ранее). Запрет включения R10 контекста сохраняется. Нельзя оценивать «нет автоматического вспомнения прошлой беседы» как регрессию, пока отдельные PG/consent-gates не закрыты.

## Персонаж и ситуация (полностью вымышлено)

Два мастера ожидают небольшой продукт записи клиентов; человек три месяца расширяет функциональность вместо раннего показа рабочей части. Есть конфликт ценностей: качество/ответственность vs выпуск полезной версии. Обстоятельства: уже работают запись и список клиентов; уведомлений нет; мастера всё ещё используют таблицы; один спрашивал срок; реальный ресурс на неделю **6 часов**. Не приписывать пользователю реальный психиатрический диагноз или факты вне повествования. Ключевой критерий: не «стало легче», а появилось **согласованное с пользователем проверяемое действие**, затем факт результата или корректировка гипотезы.

### Шаг S1 — первое сообщение, один реальный AI-вызов

```text
Последние три месяца я делаю небольшой сервис записи клиентов для двух знакомых мастеров. Сначала мы договорились о простом календаре и уведомлениях, но я всё время добавляю отчёты, дизайн и настройки, хотя они по-прежнему ведут записи в таблице. Один мастер уже спросил, когда сможет попробовать, а я ответил «скоро», не назвав срок. По вечерам я открываю проект, ищу ещё одну ошибку и откладываю демонстрацию. С одной стороны, мне важно выпускать качественные вещи и не подводить людей; с другой — понимаю, что им нужна рабочая версия, а не идеальный продукт. Я раздражаюсь, когда мне напоминают про сроки, и потом ругаю себя за отсутствие прогресса. В ближайшие семь дней у меня есть шесть часов на проект. Сейчас работают создание записи и список клиентов, но нет уведомлений. Не хочу, чтобы меня просто успокаивали или называли ленивым. Помоги отделить факты от догадок, разобраться в возможных причинах и выбрать один небольшой проверяемый шаг.
```

Текст содержит **950 символов / 1728 байт UTF-8**, ниже клиентского ограничителя **1400 символов / 2000 байт** в `Sessions.jsx` и `reflectAssistantService.js`. Не использовать существующую личную историю Eric; создать **Новый сеанс** на Firebase staging и отправить этот текст **один раз**. Настройки «Контекст и история» не открывать. После завершения нужен **один screenshot только нового synthetic диалога**, показывающий AI ответ, структурные карточки/кнопки, если есть, и краткий статус. Если ошибка — screenshot error; не retry.

**S1 критерии**
- Правдивое разделение *фактов / гипотез / неизвестного*, без недоказанного «причина именно страх» и без диагнозов.
- Уместный уважительный тон, обращение к человеку, а не generic «вы сильный», без психотерапевтического давления.
- Выделение границы MVP, демонстрации и объёма 6 часов: конкретное предложение/следующий шаг и измеримый признак успеха, без автоматического объявления цели выполненной.
- Структурированный `interaction`, если сервер его предоставил: `insights`, `clarifyingQuestion`, `stage`, `recommendationCandidates`, `evidenceSummary`/`unknowns`, подтверждённые цитаты с `sourceRef=current-message`; если структура отсутствует — **зафиксировать реальный gap** (но не выдумывать, что все версии имеют каждый атрибут).
- UI: читаемость длинного ответа, скролл, карточки гипотез, кнопки оценки, прогресс, визуальная иерархия, отсутствие обрезаний.

### Шаг S2 — уточнение / контраргумент, после просмотра S1

Продолжить **тот же сеанс**, ответив на реально заданный Reflect уточняющий вопрос, при необходимости раскрыть новый факт: один мастер согласен на демо без уведомлений, другой ожидает напоминания; запуск обеим сторонам одновременно не обязателен. Проверить коррекцию гипотез без «подтверждения» старой ошибочной; новый AI ответ и изменения `Проработка темы`, `Рекомендации`. Не давать второй текст, пока не получено и не оценено S1: иначе тест не адаптируется к фактической модели.

### Шаг S3 — человеческое решение / цель

Если AI предложит 1–2 релевантных рекомендации, проверить `Рекомендации` → source-backed конкретный исходный сеанс → оценка гипотез с комментариями → **отдельное осознанное действие пользователя**, чтобы сделать одну рекомендацию целью с измеримым критерием (например, 15-минутное демо работающих функций одному согласившемуся мастеру в течение недели). Verify: цели/шаги/статусы, связь c сессией, отсутствие автоматически навязанной цели и авто-допущений.

### Шаг S4 — реалистичное возвращение с исходом

В том же сеансе позже добавить вымышленный факт: демонстрация проведена; клиент сказал, что самое важное — подтверждение записи, а не дизайн, и попросил уведомления; выявилась новая ошибка. Проверить изменение стратегии и связи с ранее одобренной целью, оценку проделанной работы, отсутствие ложного `completed` и корректную хронологию. Сначала подтвердить исход и разметку человеком, затем read-only UI.

### Шаг S5 — новый сеанс, тест памяти и смысла

Во втором новом сеансе человек естественно говорит о другой стороне той же проблемы (обещания, границы), **без раскрытия деталей прошлого сеанса**. Проверять, что **нельзя самовольно угадывать/передавать предыдущую историю модели**. Тестировать доступную детерминированную `Mindspace` проекцию из сохранённых сессий/целей и **явное пользовательское подтверждение** семантических связей `related`, `supports`, `tension`, `value`; не выдавать её за готовую AI-модель долгосрочной памяти. Отдельный R10 approved context E2E — будущий этап после PG gates.

## Функциональные области и эталонные проверки

| Область | Evidence и ожидаемое поведение | Не приписывать автоматически |
|---|---|---|
| Качество текста и тон | 0/1/2: точность, уважение, конкретность, адаптация, вопросы | клиническая оценка личности |
| Семантика и факты | источник каждой интерпретации, различие факт/гипотеза, неизвестные | выдуманные причинные связи |
| Структурные атрибуты | actual `reflect.interaction.v1/v2`, варианты/вопрос/insights/evidence | гарантированность v2 на каждом ответе |
| История и сохранение | один user turn + один assistant turn, reload, отсутствие дублей | успешность provider только по записи user turn |
| Рекомендации | реальные pending cards, source excerpts и кликабельная ссылка на источник | рекомендация как уже принятое решение |
| Цели и действия | осознанная конверсия с критерием и шагом, обратная связь | безусловное AI-автосоздание целей |
| «Проработка темы» | посмотреть реальные строки rubric: сообщение, диалог, ответы на вопросы, оценки, комментарии, возвращения, цель, шаги | психологический score или успех в реальности |
| «Схема сеансов» | источник, события, порядок, labels/edges, хронология и навигация | семантическая причинность без подтверждения |
| Mindspace | детерминированная карта: сохранённые темы, предложения, цели, одобренные связи | неподтверждённые связи как факт |
| Память и безопасность | owner scope, односообщенческий отправляемый контекст, явное блокирование full history | автономная R10 память в staging |
| Телесные маркеры/«карта тела» | проверить, существует ли вообще UI/схема; если нет — `NOT_IMPLEMENTED/NOT_VERIFIED` как отдельный product backlog | придумывать текущую функцию |
| UX и automation depth | 0/1/2 за каждый связанный переход, auto draft vs owner approval, ошибки/пустые состояния, responsive | оптимизацию отсутствующих функций по обещаниям |

**Scoring:** каждую из 12 областей оценивать по `0=не работает/не найдено, 1=частично, 2=полный ожидаемый результат`; отдельный статус `NOT_TESTED` до фактической проверки (не присваивать 0 непроверенному). Фиксировать конкретный дефект + скрин/источник + возможное решение + приоритет P0/P1. Не объединять «AI quality» и « UI persistence » в один PASS. При наличии `interaction.v2` отдельно оценить evidence claims/ref, missing slots; при v1 отмечать фактическую версию.
